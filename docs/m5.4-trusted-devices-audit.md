# M5.4 — Persistent Device Pairing: Audit & Trusted-Devices Design

**Status:** audit complete; design approved-pending-review; implementation not started.
**Scope:** evolve QR-per-session pairing into pair-once / reconnect-forever trusted
devices, without weakening the security properties the current system already has.

Every claim below is labeled **Verified** (traced to code), **Recommended**
(design decision this doc proposes), or **Future** (explicitly out of M5.4 scope).

---

## 1. Existing pairing architecture (Verified)

### Current flow — every session, no exceptions

```
Desktop bubble click
  → POST /pairing/create            (services/pairing.ts:39)
      token: randomBytes(24), Redis EX 60s, single-use
      roomId: fresh UUID per pairing
      RoomAuthStore.recordDesktop(roomId, desktopDeviceId)   ← awaited, security-critical
  → QR rendered  { v, token, roomId, apiBaseUrl, signalingUrl, deviceName }   (protocol/qr.ts)
Phone scans (ScannerScreen)
  → POST /pairing/redeem            (services/pairing.ts:91)
      GETDEL — atomic burn, replay-proof
      RoomAuthStore.recordMobile(roomId, desktopId, mobileId)  ← awaited, before response
Phone joins WS /ws/signal
  → register (gated by RoomAuthStore.verify — registerAuth.ts:55)
  → pair-request → desktop Approve/Deny UI (Control.tsx, tray)
  → pair-approved → hub mints sessionId + per-peer time-limited TURN creds (hub.ts:386)
  → session-start → offer/answer/ICE → WebRTC session
Disconnect
  → room ends (hub.endRoom), roomStore record deleted, Redis records expire
  → EVERYTHING about the peer relationship is forgotten
```

### Components inventory

| Component | Location | Role |
|---|---|---|
| Pairing service | `apps/backend/src/services/pairing.ts` | mint/burn single-use tokens |
| Room authorization | `apps/backend/src/services/roomAuth.ts` | binds roomId → the two deviceIds it was issued to |
| Register gate | `apps/backend/src/signaling/registerAuth.ts` + `routes/signaling.ts:236` | pre-hub auth check on every `register` |
| Signaling hub | `apps/backend/src/signaling/hub.ts` (+Room/Registry/Router/LifecyclePolicy) | seats, relay, approve, session mint, grace/reap |
| Room persistence | `apps/backend/src/session/roomStore.ts` | 6h Redis records; boot-time resurrection |
| Session records | `apps/backend/src/session/manager.ts` + Postgres `sessions` | fire-and-forget persistence + audit log |
| Desktop identity | `apps/desktop/src-tauri/src/lib.rs:38` | uuid in a plain file under app-config dir, stable across launches |
| Mobile identity | `apps/mobile/src/lib/device.ts` | **in-memory only — new id every app launch** |
| Approve/Deny UX | `apps/desktop/src/components/Control.tsx`, tray (`lib.rs`), `state.rs::PendingRequest` | who's asking + which scopes + since when |
| DB scaffolding | `apps/backend/src/db/schema.ts` | `users`/`devices`/`trusted_devices` exist, **unused by any route** |
| Forward spec | `docs/m5-auth-design.md` | Ed25519 device keys + accounts (design-only) |

### Why the QR must be repeated (root cause — Verified, not guessed)

It is a **deliberate architectural simplification (M1 dev-mode), scaffolded for
exactly this upgrade** — not a signaling or WebRTC limitation:

1. **All trust is room-scoped and rooms are single-session.** The only trust
   artifacts are the 60s pairing token and the room-auth record; both are
   Redis-ephemeral and bound to one roomId. `endRoom` erases the room; nothing
   durable ever records "this phone is trusted by this desktop."
2. **Device identity is a self-asserted string** (`m5-auth-design.md` says this
   verbatim). Persisting trust against a string anyone can claim would be a
   security hole, so trust was correctly NOT persisted until identity is provable.
3. **Mobile identity isn't even stable** — `getDeviceId()` regenerates per
   launch, so there is nothing on the phone to bind trust to today.
4. The DB tables (`devices`, `trusted_devices`) and `m5-auth-design.md` show
   the persistent system was planned from M1; M5.4 is that plan coming due.

## 2. Bug audit (Verified — every item traced to code)

### BUG-1 (HIGH): room-auth expiry kills signaling reconnect after 10 minutes
`RoomAuthStore` records are written with a fixed **10-minute** TTL
(`roomAuth.ts:26`), only at `/pairing/create` and `/pairing/redeem` — never
refreshed afterward. But **every** new WS socket, including a mid-session
reconnect (phone lock, network flip, backend restart), re-runs the register
gate (`routes/signaling.ts:236` → `roomAuth.verify`). A record older than 10
minutes is gone → `verify` returns false (fail-closed) → socket closed 4403
`unauthorized_room`. Media keeps flowing P2P, but **renegotiate/ICE-restart
ride signaling — after minute 10, a session that drops its socket can never
recover its recovery channel.** The room itself persists 6h
(`roomStore.ts:36`) and resurrects across backend restarts into a state no
device is authorized to re-enter. Directly contradicts the project's #1
priority (no activity breaks connections); sessions so far were short enough
to hide it.
**Fix (Recommended, small):** make room-auth lifetime match room lifetime —
refresh TTL on every successful verified register (sliding), extend
`recordMobile` TTL to the room-store window (6h), and delete the record in
`endRoom` alongside the room record (new optional hub hook), which also closes
the minor zombie-room-recreation window a long-lived record would open.

### BUG-2 (MEDIUM): mobile device id regenerates every app launch
`device.ts` caches in memory only. Consequences today: (a) an app
restart mid-session cannot reclaim its held seat — the hub's re-register grace
explicitly matches on the same deviceId (`room.registerSeat` → `seat_reserved`),
so the phone is locked out until grace expires and the room dies; (b) audit
logs/sessions can't correlate the same physical phone across launches; (c) any
trust system would have nothing stable to bind to. The code comment says "M5
persists it" — M5.4 must do this first.
**Fix:** persist id (and the device keypair, below) in iOS Keychain / Android
Keystore via the RN keychain module.

### BUG-3 (LOW): desktop identity is a plaintext bearer string
`lib.rs:38` stores the device id in a plain file; whoever knows the string can
impersonate the desktop to the backend (documented as accepted dev-mode risk in
`m5-auth-design.md`). Becomes unacceptable the moment trust persists — fixed by
the keypair design below, not by patching the file.

### Non-bugs verified healthy while looking
- Duplicate `pair-request` after approval is ignored (`session/mod.rs:214`).
- Duplicate Approve is idempotent (`session/mod.rs:717`).
- Zombie-socket same-device reconnect eviction works (`hub.ts:317`).
- `simulate_pair_request` is debug-build-gated (`commands.rs:275`).
- Token replay impossible (GETDEL); room-auth writes awaited before QR/response.
- Both-seats-drop-within-ms race handled (`lifecyclePolicy.isSeatGoneForGood`).

## 3. Existing strengths — keep unchanged (Verified)

1. **Single-use, high-entropy, 60s pairing tokens** with atomic GETDEL burn.
2. **RoomAuthStore seat binding** — rooms aren't bearer capabilities; only the
   paired devices can claim seats. Built with an explicit upgrade seam:
   `verify(deviceId)`'s interface stays identical when the string becomes
   cryptographically proven (`m5-auth-design.md` "Interaction with the
   seat-hijack fix").
3. **The hub's whole lifecycle machinery** — seats, grace windows, zombie
   eviction, heartbeat reaping, room resurrection, capacity caps, rate limits,
   origin checks. None of it needs to change for persistent devices.
4. **Approve/Deny UX with identity + scopes + age** on desktop (Control window,
   tray, bubble) — becomes the "first-time trust" and "ring" surface as-is.
5. **Per-session, per-peer time-limited TURN credentials** minted at approve.
6. **Audit logging** (session_start/end, pair_denied) — extend with new event
   types, no new mechanism.
7. **Protocol discipline** — zod-validated envelopes, bounded fields, versioned
   QR payload (`v` lets old scanners reject a future payload cleanly).

## 4. Existing weaknesses (beyond the bugs)

- No persistent trust → QR + approve every session (**the** product gap).
- Identity is asserted, not proven (root enabler; fix is the keypair).
- Desktop only connects signaling while a pairing/session exists — there is no
  channel to *reach* an idle desktop, which any "phone calls the desktop" flow
  requires (new component, designed below).
- `trusted_devices` requires `userId NOT NULL` — unusable before accounts.

---

## 5. Security assessment of the current system (Verified)

Threat-model properties that must survive M5.4 unchanged:
- **No silent access**: desktop-side human approval before any session; visible
  indicator; panic disconnect.
- **Replay-proof bootstrap**: single-use token; QR carries no secrets.
- **Seat authorization**: only pairing-flow devices join a room.
- **Encrypted transport**: WSS signaling; DTLS-SRTP media.
- Known accepted gap (pre-M5): deviceId strings are impersonable — which is
  precisely why trust must not persist until identity is cryptographic.

## 6. Persistent trusted-device architecture (Recommended)

Two additive legs on top of the existing system; QR pairing survives untouched
as the **trust-establishment** leg.

### Identity primitive (subset of `m5-auth-design.md`, accounts deferred)
- Each device generates an **Ed25519 keypair** on first run; private key in OS
  keychain (desktop: same `security(1)` pattern the agent keystore already
  uses — `agent/llm/store.rs`; mobile: Keychain/Keystore via RN module).
- `devices.publicKey` column (additive) holds the verified public key;
  `fingerprint` stays for dev-mode continuity.
- **Challenge-response registration**: `POST /devices/register` issues a nonce,
  device returns signature, backend verifies before creating/updating the row.
  DeviceId becomes *provable*, upgrading `RoomAuthStore.verify`'s string
  in-place, exactly as the seam was designed.

### Trust establishment (first time — the only QR)
```
QR scan → redeem → pair-request → desktop Approve
                                     └─ NEW: "Trust this device" checkbox (default on)
approve + trust → backend creates device_pair row → both sides store the peer
```
`device_pairs` (new table; `trusted_devices` stays reserved for the M5 account
model, merged later):
```ts
device_pairs {
  id uuid PK,
  desktopDeviceId uuid → devices.id,
  mobileDeviceId  uuid → devices.id,
  displayName text,            // phone's name for the desktop & vice versa
  autoApprove boolean default false,   // desktop-side "Always allow"
  createdAt, lastConnectedAt, revokedAt
}
```
Phone persists: `{ pairId, desktopDeviceId, desktopName, apiBaseUrl }` in
Keychain-backed storage → populates **My Devices**.

### Reconnect (every time after — no QR)
```
Phone: My Devices → MacBook Pro → Connect
  → POST /connect/request  { pairId, nonce-signature }     (signed, replay-proof)
  → backend verifies signature + pair not revoked
  → mints roomId, RoomAuthStore.recordDesktop+recordMobile (both ids, session TTL)
  → routes a connect-request to the desktop's PRESENCE channel
Desktop (running, idle): presence socket receives connect-request
  → autoApprove? start session runner directly (same code path as today)
  → else: ring — the existing PendingRequest/Control UI, same Approve/Deny
  → approve → pair-approved → session-start → offer/answer (100% existing flow)
```
**Desktop presence channel** (the one genuinely new component): on launch the
desktop opens a standing WS to the backend and registers into a per-device
inbox (`register` with a reserved `presence:<deviceId>` room, or a sibling
lightweight endpoint). It exists only to receive connect-requests; sessions
still run in fresh per-session rooms, so the hub's room lifecycle is untouched.
Offline desktop → phone gets an immediate, honest "MacBook Pro is offline."

### Session behavior
- Disconnect never touches trust (room dies, `device_pairs` row lives).
- **Forget** (phone) / **Revoke** (desktop) sets `revokedAt` → connect-request
  rejected fail-closed; audit event `device_revoked`; in-flight session also
  torn down on revoke.

## 7. Device management UX (Recommended)

- **Phone — My Devices** (replaces the stub `DeviceListScreen`, which already
  anticipates this): paired desktops with online state, Connect, Rename,
  Forget; "Scan QR" demoted to an "Add a laptop" affordance.
- **Desktop — Trusted Devices** (new pane in the existing Control/Setup
  windows): list phones, Rename, Revoke, per-device "Always allow" toggle;
  every auto-approved session still shows the live session indicator + tray
  Disconnect/Panic, and writes audit events — "no silent access" holds because
  auto-approval is explicit per-device opt-in, revocable, and visible.

## 8. Security review of the new design (Recommended)

| Property | Mechanism |
|---|---|
| One-time pairing | unchanged QR/token flow, still single-use + 60s |
| Reconnect authn | Ed25519 challenge-response (nonce per attempt — no replay) |
| Trust revocation | `revokedAt` + fail-closed connect gate + audit log |
| Lost phone | revoke on desktop (or any future account console) |
| Multiple phones/desktops | `device_pairs` is naturally many-to-many |
| Stolen deviceId string | worthless without the private key |
| Stolen backend DB | stores public keys + hashes only |
| Silent access | default = ring + human approve; auto-approve opt-in, per-pair, visible, audited |
| Downgrade safety | old app w/o keys can still QR-pair (no trust row) — never silently granted persistence |

## 9. Migration & compatibility (Recommended)

- **Additive only**: new tables/columns/routes; no existing route changes shape.
  Old mobile builds keep QR-pairing exactly as today.
- Existing installs: first launch of the new build generates keys and
  self-registers; the next (one last) QR pairing offers "Trust this device."
  No data migration — there is nothing persistent to migrate (Verified).
- Rollback safe: disable `/connect/request` and the product degrades to
  today's QR flow.

## 10. Risks

- Presence channel is new state on desktop + backend (reconnect/backoff reuse
  the mobile signaling client's proven pattern). Medium.
- RN keychain module is a new native dependency (well-trodden). Low.
- Crypto is boring-by-design (Ed25519 sign/verify, no invented protocol). Low.
- Scope creep toward accounts — explicitly deferred to M5 proper. Guardrail:
  nothing in M5.4 may write `users` or issue JWTs.

## 11. Recommended implementation order

0. **BUG-1 room-auth TTL fix** (independent, ship immediately)
1. **BUG-2 mobile identity persistence** (Keychain id, prerequisite for trust)
2. Device keypairs + `/devices/register` challenge-response (both platforms)
3. `device_pairs` table + trust checkbox on the approve UI + pair rows on approve
4. Desktop presence channel
5. `/connect/request` + ring/auto-approve → existing session flow
6. My Devices (phone) + Trusted Devices (desktop) management UIs
7. Revocation + audit events + tests end-to-end

Each step lands green independently; the QR flow works throughout.

## 12. Final recommendation

**Extend, don't redesign.** The audit found a system that was deliberately
built with this exact evolution in mind: the seat-authorization seam, the
scaffolded schema, the forward auth spec, and the approve UX all slot in.
The only new architecture is the desktop presence channel; everything else is
additive rows, columns, routes, and two client storage upgrades. Fix BUG-1
first regardless of M5.4 — it breaks today's product on long sessions.
