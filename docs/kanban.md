# Kanban

Findings from the pre-launch review, in the order they were found. Each row was
proved from code, a failing test, production logs, or live production
infrastructure before it was written down — and several were **disproved** the
same way and are recorded as such rather than deleted.

This file exists because the list used to live only in a conversation. Six rows
(L-20, L-38 through L-42) were reconstructed from later summaries after the
earlier record was compacted away, which is the argument for the file.

**Status counts:** 239 fixed · 5 shipped · 3 partially fixed (L-243, L-247, L-251) · 1 open ·
1 blocked on something outside the code · 4 deliberately unchanged · 4 not a bug ·
1 unrecoverable (L-20). 258 rows.

"Fixed" here means _fixed at source_. Fixed, released and device-verified are
three different states and this file keeps them apart: nothing in L-227 through
L-253 has met a real device, and none of it is in a published build.

`4d34b271d0eec5353406c9b6bb78d05feaa5ab41` is on main and tagged `v0.1.32` /
`mobile-v0.1.32`. L-224, L-225 and L-226 are included, and the mobile fixes

Main CI passed on that exact SHA before the tags were pushed. `Release`
(`34267865425`), `deploy` (`34267865788`), `Mobile — iOS (TestFlight)`
(`34267863449`, TestFlight build 0.1.32 (34)) and the follow-on `site`

Verified anonymously afterwards: the GitHub release is published (not draft, not
prerelease), the site page advertises v0.1.32, `/download/Lilypad.dmg` returns

is healthy on revision `4d34b271`.

**The iOS log proves the L-224 mechanism end to end.** `Cache not found for
input keys: pods-v2-…` (the salted key wrote a fresh entry rather than restoring
the old half-contents), then `pod install (attempt 1/5)` in the workflow's
guarded step, then `Pods match Podfile.lock — skipping pod install` from the
lane — the first time that guard has ever been true. Without the codegen half of
the fix this run would instead have hit the old cache, skipped both installs and
failed the archive with no generated sources.

All sixteen rows found on 2026-08-27 (L-171 through L-188) are closed. L-189 is
the cellular control failure from 2026-08-28: video and display-switch worked
over a srflx↔srflx pair, the input DataChannel never opened. L-190 is iOS
background-suspend looking like a killed app — a brief switch already survives;
the Mac staying Active after the phone is gone is L-192.

L-191 is the TURN SSRF deny-list gap: IPv4 private ranges were blocked (and
those ERROR lines are the deny list working), but IPv6 encodings of the same
addresses were not.

L-192 is the product defect behind a swipe-killed iPhone: the hub correctly
holds the seat for a flap, but the Mac stayed Active and encoding for 45s of
media silence. Desktop now ends (and stops sending video) on `peer-status`
offline after the 15s reregister grace.

L-193 is the Ring-while-Active race on cloud: takeover started, the new room
never heard `pair-request`. L-194 is reopen-while-Active minting a new room
instead of rejoining. L-195 is a LAN rejoin `session-start` whose old-peer
`closed` event killed the desktop runner, leaving the phone on Negotiating….

L-196 is the pairing failure where the QR window never became Approve and a 201
could mint a code before the Mac sat in the room. L-197 is the false
`desktop_offline` while the Mac was still up — presence treated inbound rings
as heartbeat proof. L-198 binds LAN rooms to the device pair authenticated by
`connect/request`. L-199 and L-200 repair the two scheduled-CI failures found
on 2026-09-03.

L-204 is the shorter capability gap proved by the v0.1.28 hardware test: when
iOS closed the control DataChannel, the Mac correctly blocked input but kept
capturing and called the session Active during the trusted-rejoin grace. The
room still remains reclaimable, but all local capabilities now suspend at the
DataChannel boundary.
