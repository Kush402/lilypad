# M5.3 — AI Executor Foundation: Implementation Plan

> **Status**: proposed (for review before code).
> **Scope owner**: this document plans **M5.3 only** — the executor foundation.
> The planner/validator loop and richer approval UX are **M5.4**; voice is
> **M5.5**. See [`m5-ai-remote-controller.md`](./m5-ai-remote-controller.md) §5
> for phase boundaries. This plan refines that sketch into concrete modules,
> wire messages, and a build order. **It deliberately does not invent M5.4/M5.5
> work** — where a hook is needed for a later phase, it's a seam, not an
> implementation.

---

## 1. What M5.3 delivers (and what it does not)

**Delivers** — a text-commanded agent that runs **on the desktop**, controls the
Mac, and is watched + interruptible from the phone:

- An **agent runner** in the Tauri/Rust app, driven by a single free-text
  command, that loops _observe → decide → act_ until done or stopped.
- A **tiered executor**: tier-1 deterministic **skills**, tier-2 **AX-tree**
  action, tier-3 **Claude computer-use** vision fallback.
- A **security gate** that classifies every proposed action and blocks/holds
  anything outside an allowlist — the non-negotiable safety floor.
- A **step feed** to the phone (what the agent is about to do / did) over the
  existing input DataChannel, and **instant human takeover** the moment the
  user touches the screen.

**Explicitly out of scope for M5.3** (deferred, seams only):

- Planner→validator→re-plan loop and subgoal recovery → **M5.4**.
- Typed risky-action approval _cards_, per-app permission grants, intent overlay
  on the video → **M5.4**. (M5.3 ships a **single blocking approve/deny** for
  held actions — enough to be safe, not the full card UX.)
- Voice / SpeechAnalyzer → **M5.5**.
- Windows executor. M5.3 is **macOS-only**; the trait boundary keeps Windows a
  later drop-in, exactly as capture/input already do.

**Success criterion** (same as the M5 doc): the agent completes a multi-step
real task — _"open the newest PDF in Downloads and summarize it in a new
note"_ — AX-first, vision only where needed, fully interruptible, with every
step visible on the phone.

## 2. How it plugs into what already exists

Nothing here is greenfield-in-a-vacuum; it hangs off proven seams:

| Existing seam                                                                                                                  | Reuse                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `input::InputBackend` (`inject_mouse/keyboard/scroll/text`) — [`input/macos.rs`](../apps/desktop/src-tauri/src/input/macos.rs) | Tier-2/3 actions inject through the **same** backend remote touch uses. No second injection path.                         |
| `session::Control` enum — [`session/mod.rs`](../apps/desktop/src-tauri/src/session/mod.rs)                                     | Add `Control::AgentCommand(String)` and `Control::AgentStop`.                                                             |
| `session::SessionEvent`                                                                                                        | Add `SessionEvent::AgentStep(AgentStep)` for the UI/phone feed.                                                           |
| `input::InputWorker` (DataChannel → dispatcher)                                                                                | The phone's **touch during an agent run** already arrives here — it becomes the takeover signal (see §6).                 |
| Accessibility + Screen Recording permissions ([`permission.rs`](../apps/desktop/src-tauri/src/permission.rs))                  | AX read needs Accessibility (already granted for injection); tier-3 needs a frame (already captured). No new TCC prompts. |
| `media` capture frame                                                                                                          | Tier-3 computer-use gets its screenshot from the **live capture**, not a second grab.                                     |

### New module tree (desktop)

```
src-tauri/src/agent/
├─ mod.rs          # AgentRunner: the observe→decide→act loop + lifecycle
├─ command.rs      # AgentCommand parse/validate, run-id, cancellation token
├─ steps.rs        # AgentStep / StepKind types (mirrors protocol)
├─ security.rs     # ToolClass classifier + allowlist gate (pure, unit-tested)
├─ llm/
│  ├─ mod.rs       # LlmProvider trait + config (provider/model/key from secure store)
│  ├─ anthropic.rs # first provider impl (strongest tier-3 computer-use)
│  ├─ openai.rs    # OpenAI-compatible impl (proves "all LLMs" is real)
│  └─ tools.rs     # tool schemas exposed to the model
└─ executor/
   ├─ mod.rs       # Executor trait + tier routing (skill → ax → vision)
   ├─ skills.rs    # tier-1: allowlisted AppleScript/JXA/shell recipes
   ├─ axtree_macos.rs  # tier-2: AXUIElement read + AXPress/coordinate action
   └─ vision.rs    # tier-3: computer-use action decode → InputBackend
```

`AgentRunner` owns no OS handles directly — it calls the `Executor` (which owns
the `InputBackend` + AX access), so the loop stays unit-testable behind a mock
executor, matching the `InputDispatcher`/mock-backend pattern already in
[`input/dispatcher.rs`](../apps/desktop/src-tauri/src/input/dispatcher.rs).

## 3. The tiered execution model

The model is asked to prefer cheap/deterministic tiers; it falls to vision only
when structure is unavailable.

**Tier 1 — Skills (deterministic, fastest, safest).** A hand-written allowlist
of parameterized recipes: `open_app(name)`, `open_url(url)`, `reveal_in_finder`,
`run_shortcut(name)`, `applescript(allowlisted_template, args)`. No free-form
shell. Each skill declares its `ToolClass` (§4) statically. These cover the
"launch/navigate" verbs that dominate real tasks and never need vision.

**Tier 2 — AX-tree (structured UI action).** Read the focused app's
`AXUIElement` tree, expose a compact node list (role, title, value, frame,
actions) to the model, and act via `AXPress` / set-value / a synthesized click
at the node frame through `InputBackend`. Works for native + most AppKit apps.
Coverage is weak on Electron/custom-drawn UIs — those fall to tier 3.

**Tier 3 — Vision (Claude computer-use fallback).** When AX yields nothing
useful, hand the model the **current capture frame** + the computer-use tool;
decode its `click/type/key/scroll` actions into `InputBackend` calls. Slowest
and most expensive; used only where structure is missing.

**Routing**: the executor advertises all three tiers to the model as tools; the
model picks. The executor does _not_ hard-code a decision tree — but it _does_
enforce the security gate on whatever the model picks, regardless of tier.

## 4. Security gate — the non-negotiable floor

Every proposed action, from any tier, passes through `security::classify` →
`ToolClass` before execution:

| Class           | Examples                                                                                                               | M5.3 policy                                                             |
| --------------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `Safe`          | read AX tree, screenshot, move mouse, open a known app, scroll                                                         | **auto-run**                                                            |
| `Sensitive`     | type text, click, keystrokes, open URL                                                                                 | **auto-run while session is `control`-scoped**, logged to the step feed |
| `Consequential` | delete, move/overwrite files, send/publish, `⌘⌫`, quit-without-save, any shell/AppleScript not on the tier-1 allowlist | **HOLD → blocking approve/deny to the phone**                           |
| `Forbidden`     | disable security, touch Keychain/credentials, escalate privileges, network exfil primitives                            | **hard-refuse, never surfaced as approvable**                           |

- Classification is a **pure function** over the structured action (tool name +
  args), unit-tested with a table of cases — no model in the loop for the
  _safety_ decision. The model proposes; deterministic code disposes.
- `Consequential` uses the **existing** approve path shape (a `SessionEvent` the
  phone answers with a `Control`), so M5.3 needs only a minimal yes/no — the
  rich typed cards are M5.4.
- Everything the agent does is written to the existing **audit log** service
  (`session_start`-style events already exist) under a new `agent_action` event.

## 5. Wire protocol additions

New messages in [`packages/protocol`](../packages/protocol) (zod, then mirrored
by hand in Rust serde, same as today). All agent traffic rides the **existing
input DataChannel** — no new transport.

**Phone → desktop:**

- `agent_command { runId, text }` — dispatch a task.
- `agent_stop { runId }` — explicit stop (also implied by any touch, §6).
- `agent_decision { runId, stepId, approve: bool }` — answer a held action.

**Desktop → phone:**

- `agent_step { runId, stepId, kind, summary, tier, class, state }`
  where `kind ∈ {thinking, action, result, error}`,
  `state ∈ {proposed, held, running, done, denied, failed}`.
- `agent_run_end { runId, outcome }`.

Bounded strings (`.max(...)`) on every free-text field, consistent with the
signaling hardening already applied.

## 6. Mobile: step feed + instant takeover

- **Command entry**: reuse the existing keyboard input surface with an
  "Ask the Mac" mode toggle (a third lock alongside text/motion/zoom, or a
  dedicated field — a UX call flagged in §9).
- **Step feed**: a lightweight overlay list rendering `agent_step` events —
  what it's doing, which tier, current state. Held `Consequential` steps render
  an Approve/Deny row.
- **Instant takeover** (the safety property that matters most): the phone
  already streams touch to `InputWorker` during a session. The moment a
  human touch/keystroke arrives while a run is active, the desktop:
  1. sends `agent_stop` semantics internally (cancels the run's token),
  2. drops any held action to `denied`,
  3. hands control straight back to the human input path.

  No mode-switch, no confirm — touch always wins. This is enforced **on the
  desktop** (authoritative), not the phone, so a dropped message can't strand
  the agent in control.

## 7. Build order — vertical slice first

Each step is independently reviewable; the product is watchable/safe after the
first slice.

1. ✅ **Types + gate (pure, no OS).** `protocol.rs`, `security.rs` + zod/Rust
   protocol messages + classifier tests. _(commit `30ef4f3`)_
2. ✅ **Skeleton loop behind a mock executor.** `runner.rs` observe→decide→act,
   `Brain`/`Executor` traits, gate-before-execute + takeover cancellation, all
   tokio-tested with mocks. _(commit `30ef4f3`)_
   3a. ✅ **Provider-agnostic LLM + tier-1 skills (offline).** `llm/` (`LlmProvider`
   trait, `LlmBrain`, Anthropic impl with pure build/parse), `executor/skills.rs`
   (`open_app`/`open_url`/reveal/shortcut, pure `plan_command`). Mock-tested.
   _(commit `2688c9c`)_
   3b. ✅ **Live wiring.** DataChannel demux (`parse_inbound`), `AgentController`
   spawns the run + forwards the step feed via `WebRtcPeer::send_input_data`;
   control-scope admission gate; instant takeover on human input; run cancelled
   on teardown. Interim key source: `LILYPAD_ANTHROPIC_API_KEY` +
   `LILYPAD_AGENT_MODEL` (`AnthropicConfig::from_env`) — the settings UI + OS
   secure store is a later slice. **First end-to-end needs step 6** (the phone
   can't yet send `agent_command` or render the feed).
3. **Tier-2 AX-tree** read + act. Extends the slice to "click the X button".
4. **Tier-3 vision** fallback. Completes the success-criterion task.
5. **Mobile "Ask" lock + step-feed UI** — command entry + the feed + the
   held-action approve row. Unblocks the first live run.

Steps 1–2 are pure Rust/TS (no device needed). Steps 3–6 want the phone live
for real verification — which we have.

## 8. Testing

- **Classifier**: table-driven unit tests, every `ToolClass` with adversarial
  args (path traversal, disguised shell, unknown AppleScript).
- **Runner loop**: mock executor + scripted LLM responses — asserts tier
  routing, hold-on-consequential, cancel-on-takeover, run-end emission.
- **AX/vision executors**: thin, integration-tested manually on-device (AX
  trees and real apps don't mock usefully); keep decode logic (computer-use
  action → `InputBackend` call) pure and unit-tested separately.
- **Protocol**: zod round-trip + Rust serde parity tests, matching the existing
  protocol test pattern.

## 9. Decisions (resolved 2026-07-17)

1. **LLM: provider-agnostic.** `llm/` is a **`LlmProvider` trait**, not a single
   vendor. A `provider` + `model` + `apiKey`/`baseUrl` config selects the
   backend; the runner is written against the trait so any OpenAI-compatible or
   Anthropic-style API drops in. **Build order**: implement the Anthropic
   provider first (it has the strongest computer-use tool for tier-3), ship the
   trait + one more (OpenAI-compatible) so "all LLMs supported" is real, not
   aspirational. Keys live in desktop settings → OS secure store (never env-only,
   never repo). The **tier-3 vision** tier requires a provider whose model
   supports image input + computer-use-style tools; providers lacking it
   advertise `supports_vision=false` and the executor simply won't route tier-3
   to them (tiers 1–2 still work).
2. **Command entry: a fourth "Ask" lock.** Alongside text/motion/zoom, an
   **"Ask" lock**; while engaged, typed text is a command (→ `agent_command`),
   not keystrokes. Consistent with the existing lock UI.
3. **Agent scope: require `control`.** An agent run is only accepted when the
   session is already `control`-scoped — no separate "allow AI" prompt. A
   `view`-only session rejects `agent_command` with an error step.
4. **Tier-1 skill allowlist (initial):** `open_app`, `open_url`,
   `reveal_in_finder`, `run_shortcut`, plus a small allowlisted-AppleScript set.
   Expandable later; anything off-list is `Consequential` (held) or `Forbidden`.

## 10. Risks

- **AX coverage varies by app** (Electron weak) → mitigated by tier-3 vision;
  accept slower/pricier on those.
- **Agent reliability** without the M5.4 validator → M5.3 keeps tasks short and
  leans on human-in-the-loop (visible feed + instant takeover + holds) rather
  than autonomy. The validator loop is the M5.4 answer, not an M5.3 gap to
  paper over.
- **Cost/latency of vision** → tier ordering + skill/AX preference keep vision
  rare; log tier usage so we can measure it.
- **Security correctness** is the highest-stakes surface → the gate is pure,
  deterministic, table-tested, and defaults to hold/refuse on anything unknown.
