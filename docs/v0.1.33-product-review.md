# v0.1.33 — make Ask useful, understandable and safe

The owner tested v0.1.33 and found Ask disappointing, API-provider setup poor,
and desktop/mobile/site presentation too basic. This is the new product input.
Review baseline is release `507804f` plus documentation `bd5a842`. No application
code, settings, deployment or release was changed during this review.

**Product decision:** make the first useful Ask result easy to reach, and make
its authority and outcome clear. Adding more autonomous tools is lower priority
than making existing work dependable. Lilypad's distinction should be that a
person can leave their Mac, ask for a useful result from their phone, see what
happened, and retain control throughout.

The canonical defect ledger is [kanban](kanban.md#v0133-independent-product-and-boundary-review--2026-09-10):
18 new findings, L-260–L-277; L-247, L-251 and L-259 reopened as partial. Each row
contains the trigger, source, proposed fix and acceptance test. This brief orders
that work and specifies the experience; it is not a second defect ledger.

## What the customer should experience

1. **Prepare this Mac.** A clear home screen shows connection readiness,
   permissions, paired devices and a prominent Ask setup action. Required
   remote-control setup and optional AI setup have separate completion states.
2. **Connect my AI.** Select a familiar provider, paste its API key, select a
   usable model, and run a sample-data connection/capability check. The customer
   should not have to know an API dialect or guess a base URL.
3. **Try something useful.** Offer a few tested examples that match this Mac's
   current capabilities: summarize content in the authorized window, open a
   requested app, or create a named folder. Never advertise unavailable file
   launching, automatic form filling, or unrestricted computer control.
4. **Understand the request.** Ask shows the goal, selected Mac/window, model,
   sharing destination and relevant limits. Routine progress is concise; detailed
   action history remains expandable. An approval explains the actual effect and
   scope, with the full script available for inspection when applicable.
5. **Receive a result.** Show the result first: summary, verified artifact or
   concrete failure, plus what remains. “Completed” needs evidence, not only the
   model's finish message or a subprocess exit code. Offer a safe next step.
6. **Take control.** Stop remains available while sending, running, stopping and
   uncertain. Human input cancels autonomous work. Show when Stop is requested
   versus confirmed, and what could already have happened.

This builds on [M5](m5-ai-remote-controller.md),
[the executor plan](m5.3-ai-executor-plan.md) and shared design tokens. The older
[P5 closure](milestones.md#p5--ask-productisation--closed-no-change) predates this
explicit customer feedback; it should not be treated as evidence that today's
setup is good. Keep phone-first Ask; this brief does not require a second desktop
chat interface or a replacement architecture.

## Provider support: broad, explicit, verified

“Accept my provider's key” means accepting the provider's supported credentials
and API contract. It cannot mean treating every service as OpenAI or claiming
that any arbitrary key is valid. Ordinary subscription credentials must not be
silently treated as API credentials. Explain supported authentication in each
preset rather than enforcing a brittle list of key prefixes.

### First implementation

Provide named presets for **OpenAI, Anthropic, Google Gemini, OpenRouter and
Ollama/local** plus an advanced custom-endpoint entry. Additional presets such as
xAI, Groq, Mistral and DeepSeek enter the verified list after their adapters pass
the same contract tests. A listing is a support commitment, not a logo collection.
Enterprise/gateway endpoints requiring different authentication, deployment IDs,
headers or API versions need a real adapter/profile, not another guessed URL.

Use a provider profile with these separate concepts:

- Stable profile ID, display name, canonical endpoint origin and API dialect.
- Credential reference scoped to that profile and destination; never the raw key
  in frontend status, logs, analytics, shared state or signaling.
- Selected model ID, verified capabilities and when/how they were verified.
- Effective source (normal settings or developer override), with the actual
  non-secret destination shown consistently on both devices.
- Health state and structured error category; “saved” and “ready” are different.

The public provider name belongs in configuration and UX; retain the existing
provider-independent runner/executor boundary. Keep platform-specific key storage
behind one secret-store interface. Do not introduce one giant vendor switch into
security classification or the action loop.

### Setup screen contract

Use `Choose provider → Connect → Choose model → Test → Try Ask` as progressive
steps, with editing/back navigation and retained drafts. Default endpoints are
filled by presets; advanced endpoint fields are deliberately labeled. Changing
provider resets incompatible model/base fields and does not inherit another
origin's credential. Show a remove/disconnect action and whether a key is saved
for this exact profile. A failed save/test has a clear recovery action.

List available models when supported, filter or label by tool/vision support,
and allow a validated manual ID for gateways that lack discovery. Model listing
alone does not establish tool or image capability. Use synthetic text and images
for probes; never capture the customer's screen merely to test a key. Verify
one complete tool-call round trip, image input when selected, and bounded errors.
Enable only capabilities that are supported. Preserve existing capability values
when an unrelated setting is edited.

On the phone, show the connected Mac's Ask readiness and exact provider/model.
If setup is missing, provide a direct route to the Mac's AI settings with clear
instructions instead of letting the first real task fail. Remote key entry can
be a later supported flow only over the authenticated encrypted peer channel,
with exact target/destination review and Keychain storage on the Mac. Never route
raw keys through the backend or put them into an agent prompt.

### What the primary documentation establishes

- OpenAI provides model discovery, but the returned basic model information is
  not a complete capability certificate. Use discovery plus verified capability
  metadata/probes. [OpenAI model listing](https://developers.openai.com/api/reference/resources/models/methods/list).
- Gemini documents an OpenAI compatibility path with its own base URL and
  examples. A named Gemini preset can use that documented contract where it
  meets Ask's needs; do not infer parity for every API feature.
  [Google compatibility documentation](https://ai.google.dev/gemini-api/docs/openai).
- Ollama documents compatibility with **parts** of the OpenAI API, including
  examples for vision. Local capability still depends on the loaded model.
  [Ollama compatibility documentation](https://docs.ollama.com/api/openai-compatibility).
- Anthropic documents its own API and authentication conventions. Keep a native
  adapter instead of mapping an Anthropic key onto a compatible endpoint.
  [Claude API overview](https://platform.claude.com/docs/en/api/overview).

These sources were read on 2026-09-10. They support the integration strategy,
not a claim that all named services were tested with live credentials here.
Choose current model defaults during implementation and keep them updateable.

## Desktop: a clear home, not a collection of setup cards

Keep the bubble as the lightweight entry. Its dashboard should lead with
**This Mac is ready / Needs attention**, the active remote session, and the next
useful action. A customer should find AI settings in one obvious navigation
choice rather than infer that permissions Setup contains API-key management.

Proposed navigation: **Home · Devices · Ask settings · Privacy & history**.
Keep existing account/reachability controls and reuse established tokens. Ask
settings contains provider profiles, readiness, test result, model capabilities,
remove-key action and where observations go. Separate developer diagnostics from
customer recovery copy. An environment override must explain the effective
configuration; saving a different form must not look as if it changed the runner.

On an active session, show who has control and an unmistakable local stop/disconnect
control. Surface relevant permissions and pending updates without making every
optional feature an alarming warning. Responsive resizing, keyboard navigation,
focus restoration and screen-reader states are part of acceptance.

## Mobile: a useful task surface beside dependable control

Keep the live Mac view dominant during manual control. Use a reachable, stable
entry for **Control / Ask** and a visible session-health explanation. Do not
rearrange essential controls while a gesture, keyboard composition or task is active.

The Ask empty state should show readiness, supported examples and a real input
prompt. While running, emphasize the user's goal and current action, preserve
the existing transcript behind disclosure, and keep Stop outside a scrolling
history. An approval card should state **what changes, which app/file/destination,
and what data leaves**. Ordinary customers need a semantic explanation before
script text, but full executable content and grants must remain reviewable.

Finish with a result card and honest verification state. A denied action should
lead to a useful alternative or request for input, not a triumphant Done. Avoid
blind automatic retries after uncertain side effects. Preserve drafts across
connection failure, backgrounding and panel changes. If a task is interrupted,
show the last confirmed result and offer explicit resume/replan, never an
automatic replay of a send/delete/payment.

Accessibility targets for the redesign: touch controls at least 44 points,
Dynamic Type without clipped approvals, logical VoiceOver order, announced status
changes, reduced-motion behavior, sufficient contrast, landscape and small-phone
coverage. These are product acceptance targets; they were not visually validated
in this session.

## Website: show the experience and the boundaries

The existing page contains Ask, setup, security, pricing and download content.
Improve its hierarchy around one demonstrable use case rather than adding more
feature paragraphs. Use a real, sanitized capture of **phone request → Mac
approval/action → useful result**, labeled with the tested version. No fabricated
performance numbers or invented user endorsements.

Lead with a concise customer promise and clear Mac/iPhone availability. Keep the
Mac download, version/system requirements, and TestFlight invitation route easy
to distinguish. Explain both-device setup and BYOK before the visitor downloads;
a phone alone is not a configured remote Mac. Keep download size/version generated
from release metadata rather than hand-edited “20 MB” copy.

The Ask section should say: **actions execute on your Mac; observations go to
your chosen model provider unless you use a local model**. “Runs on the Mac”
alone is easy to misunderstand. Replace absolute safety claims with the actual
supported permission/approval behavior after the boundary fixes. Preserve clear
pricing/preview status, privacy, support and recovery instructions.

Reuse the design system across surfaces, while using each platform's native
interaction conventions. More decoration, animation or a web framework is not
itself a better product. Prototype one complete first-use journey before polishing
every screen. Review actual desktop, iPhone and Safari rendering with the owner.

## Safety and capability direction

The strongest near-term improvement is a small set of trustworthy semantic skills.
Ask currently offers app/URL/folder, AX press, scripts and optional screenshot;
it does not expose a general trusted text-entry workflow. That limits common
customer tasks such as preparing a draft or completing fields. Expanding this
requires scoped, context-aware field editing and postconditions, not silently
graduating to unreviewed global keystrokes.

Specify and test each skill's input scope, side effect, approval requirement,
verification and recovery. Reading authorized content and preparing a draft are
different capabilities from publishing it. Keep consequential approval per
material effect; reduce approval fatigue through proven narrow capabilities,
not broad “always allow everything” switches. Treat screen/AX content as untrusted
input and never let model prose waive a boundary.

Fix L-260/L-261/L-277 before expanding arbitrary scripts. Inspect output export,
error handling and cleanup as carefully as script launch. If macOS cannot provide
the required process/file boundary, temporarily restrict the capability and say
so. Keep provider independence, explicit takeover and one execution owner.

## Reliability and scalability acceptance

Scalability remains a standing requirement. Every new queue, history, artifact,
HTTP body and retry path needs a byte/work/time limit and explicit overload
behavior. Count active resources; a retention policy after success is not an
execution quota. Avoid making the async session loop wait on blocking Keychain,
AX, file traversal or provider calls. Observe failures without logging keys,
prompts, file contents or screen text by default.

Add opt-in/privacy-conscious measurements for provider setup success, time to
first useful task, verified completion rate, denial/replan rate, Stop confirmation
latency, decoder stalls and reconnect duration. Define denominators and count
unknown/interrupted outcomes separately. Per-task token/cost budgets and a clear
limit state belong in BYOK UX; do not promise exact spend for providers that do
not expose enough usage/pricing data. No external analytics dependency is needed
for the initial local evidence.

Before M11 scale-out, prove room ownership, routing, rate limits, revocation and
recovery under restart/partition with a real test backend. Do not add another
production replica or flip `ENFORCE_REMOTE_ENTITLEMENT`. The existing no-second-
replica constraint remains in force. Provider work should not move observation
payloads or API credentials through the backend.

The following remain **validation work, not newly proven customer regressions**:

## Reproducing the boundary evidence

Use only disposable fixtures. The following probes ran locally against the
released source, without production credentials or private files:

1. Generate `SandboxPolicy::read_only(scratch)` with the real
   `sandbox/profile.rs::build_profile`. Run a shell creating `output.txt` as a
   symlink to an existing synthetic file outside scratch. Verify the sandboxed
   script succeeds without changing that target. Then perform the executor's
   subsequent host-side output write: the synthetic target changes. The fix must
   keep it unchanged without granting the target to the script.
2. Generate the same profile with a writable grant to a disposable
   `home/.ssh/config`, no readable grant. A shell `printf` redirect modifies it.
   Run the same test through the full classifier/executor after implementing
   protected-write enforcement; do not use the user's real home.
3. Compile the exact released `prune_run_store`, `dir_bytes`, `started_nanos`
   helpers and constants into a small test harness. Create two 80 MiB sparse
   files in active/previous run directories and call prune. Both survive:
   167,772,160 bytes versus the 134,217,728-byte policy. No 160 MiB physical disk
   fill was necessary. Extend with canceled/error runs and idle age expiry.
4. Under the same released Seatbelt profile, start a Perl process in a new
   process group. Its child calls `POSIX::setsid`, closes output handles, waits
   two seconds and writes a scratch marker. Kill the original group after half
   a second. The marker is written. All probe descendants finish within a few
   seconds; do not leave daemons behind. The fix must prevent the late marker
   through the full runner's Stop, timeout and supersession paths.

The temporary harnesses were `/tmp/lilypad-profile-probe.rs` and
`/tmp/lilypad-retention-probe.rs` during this session. The steps above preserve
reproducibility after temporary files are removed. No full signed-app exploit or
complete absence of other defects is claimed by these probes.
